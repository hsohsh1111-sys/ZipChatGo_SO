## 2. 기획 배경과 문제

집을 찾을 때 사용자는 매물의 위치와 가격뿐 아니라 교통, 주변 편의시설, 거래 흐름, 계약상 유의점을 여러 화면과 자료에서 따로 확인합니다. 조건을 비교하고 다음 행동을 결정하는 과정이 분산되어 있어 탐색 부담이 큽니다.

집찾GO는 지도 기반 매물 탐색을 중심에 두고, 시장·주변 정보를 한 서비스 안에서 살펴보며 AI에게 자연어로 필요한 탐색을 요청할 수 있도록 기획했습니다.

## 3. 비전 및 목표

### 비전

**대화가 웹사이트의 통합 인터페이스가 되는 부동산 탐색 서비스**를 지향합니다.

### 단계별 목표

1. 현재 웹사이트와 코드 구조를 정리한다.
2. Spring Boot에서 FastAPI로 내부 요청을 전달한다.
3. FastAPI에서 OpenAI 기반 일반 대화와 상담 원칙을 적용한다.
4. 지도 화면에서 App State와 대화 UI를 연결한다.
5. 매물 검색 도구를 Spring API에 연결한다.
6. AI 응답의 제한된 UI Action으로 지도 결과를 반영한다.
7. 이후 법률 RAG, 관심매물, POI·분석, 다단계 Agent를 단계적으로 검토한다.

현재 저장소에는 AI 채팅, 매물·POI·역 검색 도구, 법률 검색 경로와 지도 UI Action 코드가 확인됩니다. 각 단계의 실서비스 완성도와 운영 데이터 연결은 요구사항 문서의 상태를 함께 확인합니다.

## 4. 대상 사용자와 대표 요구

- **주거 탐색자**: 특정 지역·가격·주택 유형에 맞는 매물을 지도에서 찾고 싶다.
- **지역 비교자**: 매물 주변 교통·교육·의료 시설과 시장 흐름을 함께 보고 싶다.
- **계약 검토자**: 부동산 계약 관련 질문의 참고 근거와 확인할 위험을 알고 싶다.
- **매물 등록자**: 매물을 등록하고 필요한 정보를 관리하고 싶다.

## 5. 제품 범위

### 현재 서비스에서 확인되는 범위

- Spring Boot 기반 웹 페이지와 API
- 지도 검색·매물 선택·POI 표시 및 검색
- 시장 동향·지표·AI 분석 리포트 화면
- 인증 관련 화면과 회원/매물 기능 경로
- 지도 화면의 AI 채팅과 FastAPI 연동
- 매물·역·POI 검색 도구, 법률 검색용 RAG 연결 코드
- 명시적으로 정의된 지도·매물·POI·관심매물 UI Action

### 후속 범위

- AI와 분석 페이지의 완전한 양방향 제어
- 관심매물 Context 및 AI 도구의 서비스 데이터 연동 범위 확대
- App Knowledge RAG, Streaming, 품질 평가·운영 로그
- 데이터 출처와 갱신 정책의 운영 수준 확정

## 6. 핵심 설계 원칙

- 부동산 도메인 데이터와 비즈니스 로직은 Spring Boot가 소유한다.
- FastAPI는 Agent·LLM·RAG·도구 선택과 응답 생성을 담당한다.
- AI에게 임의 JavaScript, `eval`, 임의 DOM 조작 또는 임의 SQL을 허용하지 않는다.
- HTML 전체 대신 필요한 App State를 구조화해 전달한다.
- 법률·변동 데이터는 모델에 고정하지 않고 검색/API 결과를 활용한다.
- 개발은 단계별로 진행하며 구현 상태와 계획을 구분한다.

## 7. 성공 기준

- 자연어 매물 요청이 Spring 데이터 조회 결과와 연결된다.
- 답변에 사용된 매물 ID와 지도에서 강조되는 결과가 일치한다.
- 허용되지 않은 Action은 실행되지 않는다.
- 데이터 미확인·외부 서비스 오류·검색 결과 없음이 사용자에게 구분되어 전달된다.
- 문서에서 구현 기능과 후속 계획을 혼동하지 않는다.
